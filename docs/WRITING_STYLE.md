# 剧情文案文风指南（去 AI 味）

- 文档状态：v0.1（2026-08-23 起）
- 适用范围：`content/test-story.json` 及后续剧情包中所有玩家可见文案
- 关联文档：[丝芭热点话题素材索引](SIBA_TOPIC_SOURCES.md)、[核心粉丝人设档案](CORE_FAN_PERSONAS.md)、[剧情数据格式](STORY_DATA_FORMAT.md)
- 配套工具：`npm run check:flavor`（启发式自检，见文末）

## 1. 总原则

本作的文案是**聊天体**：目标是让玩家截图发群时没人觉得是「模型写的」，而不是写得像散文。

- **自然 > 风格化**。别为了去 AI 味硬塞口语词；如果原句已经像人发微信，就不改。
- **减法优先**。去 AI 味先删（解释腔、总结腔、多余转折），再调（节奏、标点），最后才考虑换词。
- **保语义 > 去 AI 味**。数值、人设、剧情因果一个字都不能改坏。
- **语域一致**。一条消息里，说话方式要像同一个人、同一个场景（口袋 48 的翻牌语境）。

## 2. 已经写对的部分，不要改坏

去 AI 味最怕误伤。以下内容读起来就是真人写的，保持住：

- 具体数字细节：「数学比上次多 11 分」「昨晚一点四十还在核集资数字」「400 星梦值折 0.3 作品分」。
- 河内黑话与行业细节：易拉宝、PK 集资、明票榜、心碎 bot、知豆了、新人 top16。
- 偶像营业语气词：「哎呀宝宝~」「谢谢宝宝体谅啦~」「知豆了知豆了」。
- 碎句与错位节奏：「还有机会的。别急」「计划表当场阵亡哈哈」。
- 一句收尾的 NPC 段子：「把『进行中』写得真诚一点」「你比我们的换装还快」。
- 口语里自然的对比句：饭头说「不是因为我是饭头，只是因为我还喜欢你」，真人真的会这么说，保留。

## 3. 本包实测的 AI 味模式（附改写）

### 3.1 「不是 A，而是 B」对比句

AI 最爱用否定来引出结论。改写规则：**删掉否定，直接说 B**。但见第 2 节：说话人身份自然时保留。

> ❌ 「这才是今天最值得汇报的事：你没有偷偷硬撑，而是把喜欢和自己的生活一起讲清楚了。」（yuzu-05）
> ✅ 「今天这件事最该夸：你没硬撑，还跟妈妈把喜欢我这件事讲明白了。」

> ❌ 「名字被念出来时，你先想到的不是那张最高的票仓标签，而是这三十天里每一次决定把谁放在前面。」（rank-rookie）
> ✅ 「名字被念出来时，你脑子里全是这三十天回过的每一条翻牌。」

> ❌ 「不是传说里的奇迹，但你的名字出现在了更靠前的位置。」（rank-stage）
> ✅ 「没有奇迹，可你的名字确实往前站了。这三十天回的每一条翻牌都算数。」

### 3.2 说教腔 / 三段式标准答案

偶像回复写成「肯定 → 道理 → 升华」的三段范文，是全场最重的 AI 味来源。**长回复本身不是问题**；历史翻牌里长回复很多，真正显假的是每句都完整、每段都平均、最后还要总结。规则：先删抽象道理和升华，只留下具体反应、动作、个人岔题与真正需要说的话；必要时再拆短。

> ❌ 「十二票当然有意义，但它不是你的大小。奶茶和喜欢的笔袋也属于你的生活，不要每次喜欢我都先从自己身上减东西。你能来告诉我这些，就已经不是一个小数字了。」（yuzu-03 life-first）
> ✅ 「十二票哪里小啦。奶茶不许戒，笔袋也去买。喜欢我不用先从自己身上抠，你肯把这笔小账算给我听，这十二票就比谁都大。」

### 3.3 同一意象全包复用

AI 会把一个漂亮的抽象意象反复用。本包实测：

- 「属于我们 / 属于你 / 属于她」× 4：yuzu-03、battery-01、battery-02b ×2。**全包保留 1 处**（建议留 battery-02b 主线），其余换具体说法。
  > ❌ 「那以后给我多留一点不属于她的时间。」
  > ✅ 「那以后把你的时间多分我一点。」
- 「作废」× 2：lighthouse-03 与 battery-03 各用一次。
  > ❌ 「这些年不会因为一次争吵作废。」（battery-03）
  > ✅ 「一次吵架，抹不掉你追过的每一场公演。」

### 3.4 结尾升华句

「原来……真的可以改变一些事」这类句尾拔高，删掉，**停在具体画面上**。

> ❌ 「灯光落下来以前，你先看见了台下几张熟悉的脸。原来{{cityName}}的三十天真的可以改变一些事。」（rank-breakout）
> ✅ 「灯光落下来以前，你先看见了台下几张熟悉的脸，和一堆你叫不出名字的新灯牌。」

> ❌ 「票数不够漂亮，但故事没有被清零。只是下一次营业前，你需要先学会照顾自己。」（rank-next-year）
> ✅ 「票数不好看，但这三十天回过的消息都还在。明年再来，先把觉睡够。」

### 3.5 自我注释 / 元评论

角色解释自己正在说的话（「解释不是挽留」），是典型的 AI 自审痕迹。

> ❌ 「解释不是挽留，但我不想让你以为那两次认真回复都是假的。」（patron-goodbye）
> ✅ 「那两次回复，没一条是应付你的。」

### 3.6 格言式 bio 对仗

bio 允许短句，但避免「对仗格言 + 热词」组合。

> ❌ 「把正常营业理解成特殊感情，也把私人行程说成巧合。」（salt）
> ✅ 「营业当暧昧，跟踪当偶遇，还觉得是你先动的心。」

> ❌ 「见过很多小偶像的冷静神豪，只为值得的情绪价值停留。」（patron）
> ✅ 「见多了小偶像的神豪，花钱前先看你值不值。」

### 3.7 程度词与强调拐杖

- 「真正」× 5、「永远」× 2：多数可删，或换成「真」。
- 「特别特别开心」（patron-01）反而像真人，保留。
- 全包避免：「仿佛 / 宛如 / 犹如 / 不禁」「然而 / 与此同时 / 不仅如此 / 值得一提」「总而言之 / 总之」。

### 3.8 破折号与省略号纪律

- 「——」全包建议不超过 2 处；lighthouse-04-choice 那处保留。
- 中文省略号用「……」；聊天场景允许少量「...」，但别通篇都是。

### 3.9 历史翻牌的表面节奏基线

2026-09-04 对本地历史记录的 760 条粉丝消息和 619 条文字回复做过角色分离统计。语料存在明显偏置：759 条粉丝消息来自同一账号，95.3% 的文字回复来自两名成员，因此这些数字只用于校准节奏，不能当作所有粉丝和所有成员的统一模板。

- 粉丝消息中位数约 120 字，71.7% 含换行、60.4% 使用空行分段；只有 2.8% 使用问号，但大量消息通过「怎么 / 有没有 / 想知道」完成提问。粉丝侧允许逗号串句、裸停和一条消息并列两三个话题。
- 成员文字回复中位数约 196 字，86.8% 含换行、73.8% 含 emoji；感叹号、重复标点和反问明显多于粉丝侧。选项为了可比较可以更短，但不应全部压成一句完整书面句。
- emoji 不是全局装饰。每个成员应有独立的爱称、笑声、语气词、emoji 组合和分段习惯；普通、兴奋、安慰、边界四种场景再调整强度。
- 轻松回复可以先反应再回答，允许临时岔题；认真安慰和设置边界时自动减少 emoji、缩短句子，不需要强行活泼。
- 全角波浪号「～」优先于 ASCII `~`。emoji 更像情绪拍点：同类连续 2–4 个通常比每句换一种自然，但不能机械地每条都加。

## 4. 分角色语感基准

| 角色                     | 语感                           | 规则                                                                                                                                                                   |
| ------------------------ | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 偶像（玩家 choice 回复） | 营业语 + 真实感，按投入分层    | 低投入可以 1–2 个节拍；高投入允许 2–4 个不对称段落。带语气词、具体细节、追问或个人岔题；禁止「肯定 → 道理 → 升华」和「把 X 与 Y 讲清楚」类抽象。营业套话一天最多一句。 |
| yuzu（学生粉）           | 句子短，把小事当大事汇报       | 情绪外露、爱用「哈哈」「！」，但别每句都感叹。                                                                                                                         |
| salt（私生）             | 自我中心、短促逼问             | 偶尔示弱；消息不该工整。                                                                                                                                               |
| lighthouse（饭头）       | 工作感：数字、业务黑话、真抱怨 | emoji 少；「不是…而是」在这里最自然，可以多用一点。                                                                                                                    |
| battery（单推王）        | 傲娇、简洁、带讽刺             | 半分钟梗这种具体细节是她的辨识度。                                                                                                                                     |
| patron（神豪）           | 极简、观察者视角               | 要求直给；他不写长句。                                                                                                                                                 |
| 普通 NPC 闲聊            | 微博/群聊搬运感                | 先事实后吐槽，punchline 一句收尾。                                                                                                                                     |
| 结局/成就 description    | 截图文案感                     | 一句具体画面 + 一句情绪；禁止「原来……真的……」升华。                                                                                                                    |
| `context` 等制作层字段   | 讲机制即可                     | 不需要人味，说清楚触发条件。                                                                                                                                           |

## 5. 保存前自检清单

- [ ] 这条消息里有「不是…而是」吗？删否定直接说结论（口语自然的除外）。
- [ ] 把情绪直接解释出来了吗（“我感到…”“这让我…”）？换成动作或生理细节。
- [ ] 结尾有升华句吗？删，停在具体画面。
- [ ] 这个意象（属于/作废/光/风…）在别处用过吗？全文最多一次。
- [ ] 偶像回复超过 2 句时，是否每句都过于完整、每段都在讲道理？删抽象总结，保留具体反应和不对称节奏；不要只因长度删掉真人感。
- [ ] 有「真正/永远/值得/最」吗？删掉再读一遍，不通再回填。
- [ ] 能不能在真实翻牌的节奏里找到同类说法？按那个节奏改写（素材边界见 [SIBA_TOPIC_SOURCES.md](SIBA_TOPIC_SOURCES.md)）。
- [ ] 读出声。像不像人发微信？（标准是“像”，不是“文笔好”。）

## 6. 自动化自检

```powershell
npm run check:flavor              # 输出报告，退出码恒为 0（advisory）
npm run check:flavor -- --strict  # 有命中即以退出码 1 失败，可进 CI
```

脚本扫描玩家可见字段，报告对比句、「真正/永远」「属于」「作废」「情绪价值」等模式计数、按节点定位和“≥60 字且至少 3 个句号”的连续完整句式。**它是启发式提醒，不是判决**：

- 命中的不一定是 AI 味（如 lighthouse-04-choice 的「不是因为…只是…」应保留）。
- 没命中的不一定没问题（如说教腔、升华句靠语感识别，脚本抓不全）。

下一步建议：把同样的模式列表接入编辑器的「剧情检查」面板，作为 warning 级检查随保存实时提醒（当前未实现）。
