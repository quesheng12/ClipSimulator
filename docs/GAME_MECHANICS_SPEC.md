# 《Clip Simulator》游戏机制规范

- 文档状态：可实现规范 v0.17
- 创建日期：2026-08-22
- 适用范围：首个可玩版本
- 相关参考：[口袋偶像类 UI 参考](../references/ui-pocket48/README.md)

## 1. 产品目标

《Clip Simulator》是一款面向 48 系粉丝的手机端轻量网页叙事游戏。玩家扮演一名虚构的 48 系小偶像，在约 30 个游戏日内处理核心粉丝的翻牌，最终进入年度总选。

游戏应满足以下目标：

- 单周目控制在 20 分钟以内。
- 点击链接即可开始，不要求注册或登录。
- 使用纯静态网页运行，不依赖业务服务器。
- 自动保存到浏览器本地。
- 以简单选择、快速反馈和高梗密度为主要体验。
- 适合玩家截图和传播结局、票数及成就。

## 2. 设计原则

玩家只需要理解以下概念：

1. 当前日期和翻牌期限。
2. 精力与心情。
3. 核心粉丝好感度。
4. 泛人气。
5. 年度总选票力。

剧情标记、节点条件、票力映射和事件判定属于制作层，不要求玩家学习。

首版明确不加入以下系统：

- 金钱、钱包或消费管理。
- 背包、物品和食物选择。
- 角色升级、技能树或装备。
- 运营评价、压力值、粉圈稳定度等额外常驻属性。
- 每日任务奖励、签到或抽卡。
- 玩家自由输入回复。
- 联网账号、云存档、排行榜或多人功能。

### 2.1 玩家身份

- 玩家扮演的是一名 18 岁左右的年轻女偶像，刚加入虚构 48 团体、离入团后的第一次总选还有 `config.totalDays` 天。她的职业体系只包括公司安排与 stf（工作人员）协助，不设经纪人；台词、剧情与文案都不得出现经纪人、驾照、酒局等超出该年龄与偶像职业的设定。
- 首次进入游戏且本地没有有效 `PlayerProfile` 时，先进入身份设置页，再进入成员主页。
- 身份设置页只用一段短文建立背景：玩家是刚加入虚构 48 团体的 18 岁新人小偶像，离入团后的第一次总选还有 `config.totalDays` 天，并以“你会怎么回复粉丝翻牌？”引出核心操作；此处不提前展开资源、好感或票力规则。
- 玩家先从 6 张内置原创头像中选择一张，再填写偶像姓名并选择所属队伍。头像包含 3 张日常少女偶像风人物照与 3 张宠物/玩偶照，不采用舞台照、不使用外链或现实成员照片；姓名可以手动输入，也可以从内容包 `profileSetup.namePools` 的改编/原创两池生成，随机结果仍可继续编辑。
- 同一次身份表单中的前三次姓名建议都来自改编池。首次身份设置的自动初始值计为第一次；两个池都有内容时，从第四次起每五次为一组，将两次改编与三次原创的来源顺序洗牌后抽取。
- 原创池允许为空。为空时所有抽取都安全回退到改编池；当前测试内容包采用这一配置，只从 SNH48 四队现役快照对应的 70 个虚构改编姓名中生成建议。
- 姓名建议的约束随机只改善命名气质与变化感，不向玩家展示来源标签，不进入存档、属性或结局计算；关闭身份表单后无需延续抽取序列。
- 姓名去除首尾空格后不能为空，最多 16 个字符。所属队伍必须引用内容包 `profileSetup.teams` 中存在的稳定 `teamId`。
- 姓名和队伍只决定成员主页及模板剧情中的身份文案，不额外增加队伍数值、加成或专属玩法。
- `PlayerProfile` 包含 `idolName`、`teamId` 与稳定的应用内 `avatarId`，使用独立本地键保存，不属于单周目 `GameState`。旧存档缺少头像或头像 ID 已失效时回退到第一张内置头像，不使身份失效。
- “放弃进度，从头开始”只重置周目，不清除身份。玩家可以从成员设置修改身份；保存后立即刷新模板文案，不改变当前资源、好感度、剧情标记或总选计算。
- 本地身份失效时，例如内容包删除了已选队伍，游戏返回身份设置页要求玩家重新确认，不静默选择其他队伍。

## 3. 周目结构

### 3.1 时间

- 一周目覆盖约 30 个自然日。
- 正常流程约 10 个回合。
- 默认每回合推进 3 个自然日。
- 建议回合日期为第 1、4、7、10、13、16、19、22、25、28 日。
- 第 10 回合结束后进入年度总选。
- 翻牌页右上角显示“离总选结束还剩 X 天”，其中 `X = max(0, totalDays - currentDay)`；`totalDays` 来自当前剧情包配置，`currentDay` 来自当前存档。

特殊事件可以改变单个回合的日期推进量，但整个周目仍应在约 30 日时收束。

### 3.2 翻牌期限

- 每条核心翻牌默认拥有 7 个自然日的回复期限。
- 期限按自然日 24:00 计算。
- 未到期的翻牌可以留到后续回合处理。
- 到期仍未处理时，执行该节点的过期结果。
- 过期可以降低好感度、设置剧情标记或改变后续节点，但普通情况下不直接终止周目。

### 3.3 单回合流程

1. 日期推进与回合开始结算。
2. 恢复固定数量的精力和心情。
3. 应用本回合特殊事件带来的恢复修正。
4. 生成新翻牌并处理已过期翻牌。
5. 更新普通粉丝的已回复会话记录。
6. 玩家处理核心粉丝翻牌。
7. 玩家可选择点一次外卖恢复资源。
8. 玩家选择“几天后”；末回合改为“进入总选”。
9. 自动保存并推进日期。

## 4. 内容规模

- 首版使用 4 至 5 名核心粉丝。
- 每名核心粉丝拥有独立故事线。
- 每条故事线建议包含 4 至 5 次关键翻牌。
- 一周目约有 20 至 24 次需要玩家选择的翻牌。
- 每回合平均出现 2 至 3 条可处理的核心翻牌。
- 每条翻牌提供 2 至 4 个预设回复，通常使用 3 个。
- 其他粉丝作为普通 NPC；普通闲聊和热点玩梗都按配置日期自动显示在已回复区，不向玩家索取回复，也不参与票力分支。

普通粉丝主要承担世界观、节奏、河内梗和一次性笑点，不消耗玩家资源。同一 `contactId` 可以跨日期形成多轮会话；每轮统一为一问一答（粉丝一条消息、成员一条回复），粉丝要聊多件事就写进同一条长消息，与真人翻牌一致。数据层仍支持可选的只读连续气泡，但内容包不再使用。

- 跨粉丝联动：一条支线的事件可以成为另一名粉丝时间线上的新翻牌（如私生回踩的余波烧进学生粉的家庭群、神豪观察饭头的组织状态），通过 `trigger` 引用其他支线设置的 flags 实现；联动节点文本必须自足，不假设玩家看过源头事件。

### 4.1 翻牌收件箱

- 翻牌首页不使用状态标签页。“未回复”和“已回复”会话同时展示在一个连续消息列表中：未回复在前、已回复在后，中间使用不可交互的“已回复” splitter 分隔。
- “未回复”按翻牌 StoryNode 逐条展示，并按回复期限由近到远排序。
- 同一名核心粉丝同时积累两条未回复翻牌时，应显示两行。每行分别使用自己的消息预览，并在右上角显示该条翻牌的“还有 X 天过期”；未回复区不合并联系人，也不使用待回复数量徽标。
- 每条未回复都可以独立点入和选择回复，玩家不必按同一粉丝的固定顺序处理。完成或过期一条只移除对应的未回复行，同一粉丝的其他待处理翻牌继续保留。
- “还有 X 天过期”中的 `X` 为当前游戏日到该条翻牌期限之间剩余的自然日数；待处理状态不得显示负数，节点过期后应先执行过期结算再更新列表。
- `deadlineDay` 为该翻牌的截止日，`nextTurnDay` 为玩家点击“几天后”将到达的下一回合日期。在非末回合中，仅当 `nextTurnDay > deadlineDay`、即本次推进后该翻牌会被结算为过期时，该行的“还有 X 天过期”使用 danger 红色强调；`nextTurnDay = deadlineDay` 时下一回合仍可回复，继续使用普通弱化色。
- 末回合点击主操作会直接进入总选，不进行下一回合的翻牌过期结算，因此不得套用上述 danger 预警条件。
- 临期状态的文字仍必须完整包含“过期”含义，且无障碍名称包含相同的剩余天数和过期语义。danger 颜色只加强紧迫感，不得成为唯一提示。
- splitter 下方的已回复区域按联系人聚合；核心粉丝会话始终置顶在普通粉丝之前，各组再按最近活动日期倒序。
- 当已回复区域中某个联系人的最新一条翻牌为过期状态时，列表预览显示该条翻牌的具体正文，右上角显示“已过期”，不得用泛化占位文案替换正文。
- 核心粉丝和普通粉丝使用相同的列表行和聊天布局，玩家界面不显示“核心/NPC”等制作层身份标签。联系人姓名下方展示内容定义的人物属性标签：核心粉丝使用 `fans[].tags[]`，普通粉丝使用当前消息的 `backgroundFlips[].tag`。
- 同一组人物属性标签必须同时出现在消息列表和聊天页联系人标题中，顺序一致；标签允许换行，不得为了固定行高静默截断。
- 聊天页展示该联系人所有已经到达当前存档的历史消息，不得展示未解锁或未选择分支。
- 已经认识一段时间的核心粉丝可以配置 `pastChats`。这些赛前聊天从第 1 日起出现在已回复会话最前方，使用“三个月前”“出道第 18 天”等作者时间标签，不伪装成第 0 日，也不写入周目存档或参与任何数值结算。真正首次出现的粉丝应保持空历史。
- 聊天中的每条翻牌都单独显示“第 X 日 24:00”，`X` 取该条内容的剧情日期；同一天的多条翻牌也不合并为一个共享日期标记。
- 过期翻牌在聊天中保留原始正文，并额外显示明确的过期状态及截止日；不能只显示“已过期”而隐藏玩家错过的内容。
- 只有从某条未回复行打开、且对应 StoryNode 在当前存档中仍可处理时才提供该条翻牌的回复选项；从已回复联系人行进入的会话、普通粉丝会话与已完成翻牌只展示历史。
- 普通 NPC 内容到达配置日期后直接进入已回复区，并按 `contactId` 聚合；它不进入未回复计数、不设置过期时间，也不出现回复选项。
- 普通 NPC 的闲聊统一为一问一答：聊天中显示 NPC 左侧消息和成员右侧回复，不进入回复结果页，也不结算资源、好感、泛人气或 flags。数据层保留可选的只读连续气泡（一条主消息加最多四条连续左侧气泡），但内容包不使用。
- 翻牌工作台底部固定操作栏，常规回合提供“点外卖”和“几天后”，末回合将“几天后”替换为“进入总选”。
- 固定操作栏必须贴住可视窗口底边，即 `bottom: 0`，不得留外边距或在宽屏下增加额外底部偏移。其外部宽度必须和 phone frame 一致；宽屏下随 phone frame 居中，底栏不得扩展到整个桌面视口。
- 底栏背景必须从按钮区连续覆盖到底部安全区且保持不透明，长列表内容不得从底栏下方或背景中露出。翻牌页面同时预留底栏的完整外部高度（按钮区加设备底部安全区），确保最后一条消息、空状态和聚焦控件可以完整滚动到底栏上方。

### 4.2 预设长回复

- 长回复仍然是普通 `StoryChoice.text`，不新增长文类型，也不允许玩家自由输入。
- 候选回复卡、发送结果和历史聊天气泡必须显示同一份完整正文并保留作者输入的段落换行。
- 长回复不折叠、不截断、不增加“展开全文”或二次确认步骤，也不在单张卡片内部建立滚动区域；页面文档负责自然滚动，资源消耗信息排在完整正文之后。
- 编辑器在回复正文超过 140 个字符时显示软提醒，帮助作者控制单周目 20 分钟的阅读量。该提醒不是结构错误，不阻止保存、导出或游戏读取。

## 5. 玩家资源

### 5.1 精力

精力表示组织语言、回忆聊天记录、撰写长回复和持续营业的能力。

### 5.2 心情

心情表示处理质问、负面情绪、越界话题和粉圈冲突的承受能力。

### 5.3 消耗规则

- 每个回复选项都必须消耗至少 1 点精力和 1 点心情。
- 不同回复可以拥有不同的消耗倾向。
- 资源只限制当前可以选择的回复，不直接参与好感度、票力或结局计算。
- 资源不足时，对应回复不可选择。
- 玩家可以保留翻牌到后续回合，或让其自然过期。

典型消耗方向：

| 回复类型   | 精力倾向 | 心情倾向 |
| ---------- | -------: | -------: |
| 简单营业   |       低 |       低 |
| 认真长回复 |       高 |   低至中 |
| 安慰粉丝   |       中 |       中 |
| 回应质问   |   低至中 |       高 |
| 设置边界   |       中 |       高 |
| 高风险玩梗 |   低至中 |   低至中 |

### 5.4 回合恢复

- 每回合开始时，精力和心情分别恢复固定数值。
- 恢复后不能超过各自上限。
- 某些回合事件可以增加或减少本回合恢复量。
- 特殊事件修正只影响当回合，不默认永久改变恢复规则。
- 精力上限、心情上限、基础恢复量及事件修正值属于后续平衡参数。

### 5.5 日初结算与节点触发

进入新一天时按固定顺序完成一次结算：

1. 推进自然日并重置本回合外卖使用次数。
2. 结算超过回复期限的待回复翻牌，记录过期并应用 `onExpire` 效果。
3. 应用当天特殊事件与资源恢复。
4. 集中检查所有已到发布日期、且前置连线已解锁的剧情节点触发条件。

默认情况下，回合内回复、设置剧情标记或点外卖只改变状态，不在当天中途插入新条件节点；新满足的节点等到下一次日初检查。回复选项可以把自己连接的下游节点设为“回复后立即出现”：回复效果先结算，引擎随后只检查该目标节点；发布日期不晚于当前日且触发条件满足时，它立即进入待回复列表，否则保持解锁并等待之后的日初检查。该设置不会激活当天其他根节点或其他故事线。外卖次数达到坏结局阈值仍立即结束游戏，因为提前结局判定不属于剧情节点触发器。

## 6. 点外卖

点外卖是回合内的资源透支机制，不扩展成金钱或道具系统。

### 6.1 基础规则

- 每回合最多点一次外卖。
- 点外卖同时恢复固定数量的精力和心情。
- 恢复不能超过资源上限。
- 每次使用都会增加本周目的累计点单次数。
- 外卖种类、价格和送达时间不参与玩法。

### 6.2 过量坏结局

- 累计点单次数达到设定阈值时，立即触发外卖相关提前坏结局。
- 该结局先中断当前分支并收录到图鉴；玩家查看后可以恢复到第四次点单之前，继续当前周目。
- 当前测试包的结局标题为“胖成一条蛆，耻辱退团”，并展示完全虚构的 JBS48 超话投稿截图；账号、头像、正文与表情包均不指向真实人物。
- 结局解锁后收录到主菜单的结局图鉴。
- 累计点单次数只用于存档和提前结局判定，不在翻牌底部操作栏中展示；底栏可以保留本次恢复量与本回合是否可点的状态。
- 具体恢复量和坏结局阈值属于后续平衡参数。

外卖系统不得继续增加营养、体重、健康或金钱等长期属性。

## 7. 核心粉丝好感度

### 7.1 基础规则

- 每名核心粉丝拥有独立好感度。
- 好感度范围暂定为 0 至 100。
- 每名粉丝可以拥有不同的初始好感度。
- 回复、翻牌过期和少量剧情事件可以改变好感度。
- 单次变化优先使用易感知的整数，例如 5、10、15。
- 每条预设回复必须显式设置当前粉丝的变化数值；无变化也写为 0。
- 好感度不会随时间自动衰减。

### 7.2 游戏模式

玩家在成员主页设置中选择显示模式：

- 标准模式：回复后显示明确的好感度变化数值。
- 拟真模式：隐藏好感度数值，只显示“上升 / 下降 / 不变”。

两种模式共享完全相同的剧情、资源、好感度、票力和结局规则。模式只改变信息展示，不维护两套平衡。

回复选项在选择前不显示其好感度结果。回复后只展示好感变化记录：标准模式显示带正负号的数值，拟真模式显示变化方向。界面同时使用图标和文字，避免只靠颜色传达结果；系统不生成结算评语。

模式同时记录为本地显示偏好和当前周目存档字段，可以在周目中途从设置切换并即时生效。点击成员主页的“翻牌”会直接新建或续玩当前周目；“放弃进度，从头开始”只位于设置中。

## 8. 泛人气

泛人气表示核心粉丝之外的整体粉圈态度。

- 泛人气范围暂定为 0 至 100。
- 泛人气不限制玩家行动。
- 只有具有公开传播性质的回复或事件才能改变泛人气。
- 普通私人交流默认只改变对应核心粉丝的好感度。
- 泛人气在标准模式和拟真模式中都可以显示。

可能影响泛人气的内容包括：

- 回复被截图传播。
- 玩梗出圈或引发误解。
- 对争议话题公开表态。
- 公演 MC 表现。
- 处理粉丝冲突。
- 总选前拉票发言。

## 9. 剧情结构

### 9.1 总体模型

剧情底层使用可收拢的有向无环图，而不是无限扩张的严格树形结构。

- 每名核心粉丝拥有一份独立故事图。
- 每个故事节点代表一次核心翻牌。
- 回复选项连接至后续翻牌节点。
- 后续节点可以同时受到前置选择和日期条件限制。
- 分支可以在后续节点重新汇合。
- 不允许形成循环依赖。

### 9.2 交叉故事线

- 一次交叉事件最多关联两名核心粉丝。
- 同一故事线内部使用明确的节点连接。
- 跨故事线影响优先使用共享剧情标记，而不是直接跳入另一份故事文件。
- 编辑器可以将设置标记与读取标记之间的关系显示为虚线依赖。

### 9.3 剧情结果

剧情选择可以产生以下效果：

- 消耗精力和心情。
- 改变对应粉丝好感度。
- 在公开事件中改变泛人气。
- 设置或移除剧情标记。
- 指定后续故事节点。
- 指定后续节点在日初检查或回复后立即出现。
- 设置一次特殊总选票力修正。

玩家不直接看到剧情标记。

## 10. 年度总选

只要玩家没有主动放弃进度，查看并返回特殊结局后，当前周目仍可继续进入年度总选。

### 10.1 核心粉丝票力

- 每名核心粉丝拥有不同的最大票力上限。
- 每名粉丝配置自己的好感度至票力映射表。
- 普通总选结果以最终好感度决定该粉丝的实际票力。
- 高票力上限可以体现消费能力、组织能力或号召能力，但不额外增加玩家需要管理的属性。
- 特殊剧情可以对该粉丝的票力执行一次加成、禁用或联合应援修正。

### 10.2 背景票力

- 泛人气通过独立映射表转换为背景粉丝票力。
- 泛人气票力不拆分为具体普通粉丝。

### 10.3 最终计算

```text
核心粉丝实际票力总和
+ 泛人气对应的背景票力
+ 极少数剧情特殊修正
= 年度总选最终票数
```

总选结果页面应展示：

- 每名核心粉丝的最终关系状态。
- 每名核心粉丝贡献的票力。
- 泛人气贡献的背景票力。
- 最终票数与名次。
- 本周目核心结局文本。
- 解锁的成就和可分享结果卡片。

## 11. 提前结局与图鉴

- 提前结局由明确行为或特殊剧情触发。
- 资源归零本身不直接触发提前结局。
- 任一回复选项可以通过 `endingId` 直接触发一个特殊结局；它不能同时配置 `nextNodeId`。
- 进入特殊结局前保存触发操作之前的周目快照。结局页的主操作为“回到上一回合”，恢复该快照，不清空身份、资源、粉丝关系或更早的剧情进度。
- 已获得的提前结局永久记录在本地结局图鉴中。
- 外卖过量是首个确定的提前坏结局。

## 12. 本地存档

游戏不依赖服务器，使用浏览器本地存储。

至少保存以下内容：

- 存档版本。
- 当前模式。
- 当前日期和回合。
- 当前精力、心情及当回合恢复修正。
- 每名粉丝的好感度。
- 泛人气。
- 当前待处理翻牌及其期限。
- 已选择的回复。
- 剧情标记。
- 累计外卖次数。
- 已解锁成就与结局图鉴。

每次选择回复、点外卖、选择“几天后 / 进入总选”和触发结局后自动保存。剧情内容与存档状态必须分离，存档不得保存 UI 或渲染对象。

玩家身份另存为独立 `PlayerProfile`：

```json
{
  "idolName": "沈星禾",
  "teamId": "team-n",
  "avatarId": "cafe"
}
```

它与周目存档、模式偏好、成就和结局图鉴分别保存。“放弃进度，从头开始”或内容版本导致周目失效时仍保留身份；只有玩家清除站点数据或身份本身不再通过校验时才重新进入身份设置。

## 13. 剧情内容文件

首个可玩版本使用单一完整内容包，避免拆分文件后产生加载顺序和跨文件引用问题：

```text
content/
└─ test-story.json
```

数据量增长后允许在编辑器内部拆分展示，但保存给游戏的仍是一个经过校验的 `StoryPack`。正式字段说明见 [剧情数据格式](STORY_DATA_FORMAT.md)。

内容包 schema v14 使用：

- `profileSetup.namePools.adapted`：命名气质改编后的虚构姓名库。
- 当前测试包的改编姓名保留参考成员的姓氏、字数与读音轮廓，通常只替换一个同音、近音或近形字；目标是让熟悉原名的粉丝可以辨认，但不直接使用完整真人姓名。
- `profileSetup.namePools.original`：可为空的完全原创姓名库；当前测试包为空。
- `profileSetup.teams`：可选队伍及 `id`、完整名称、简称、队标文字与主题色。
- `globalVariables`：由作者配置的静态字符串变量。
- `fans[].tags`：每名核心粉丝 1–4 个不重复的简短人物属性标签，用于消息列表和聊天页快速识别。
- `fans[].pastChats`：每名核心粉丝 0–8 条赛前聊天；每条记录包含稳定 ID、关系时间标签、粉丝消息和成员旧回复。数组顺序就是展示顺序。
- `nodes[].choices[].endingId`：可选的特殊结局 ID；编辑器通过回复卡片中的“特殊结局”下拉框维护。
- `nodes[].choices[].nextNodeTiming`：可选的后续节点出现时机；省略或 `day-start` 保持默认日初节奏，`immediate` 在回复效果结算后立即检查目标。
- `nodes[].choices[].effects.affinity[node.fanId]`：必填的当前粉丝好感变化数值；交叉影响仍可在同一对象中追加其他粉丝 ID。
- `nodes[].choices[].effects.popularity`：必填的泛人气变化整数；每个回复都可在编辑器中手动填写正数、负数或 0。
- `earlyEndings[].image`：提前结局的可选本地配图，包含静态资源路径 `src` 与承载剧情信息的无障碍替代文本 `alt`。

### 13.1 文本模板

- 正式身份占位符为 `{{idolName}}`、`{{idolNickname}}`、`{{teamName}}`、`{{teamShortName}}`。其中昵称取去除首尾空格后的姓名最后一个字并重复两次，例如“沈知夏”生成“夏夏”。
- 作者可以在顶层 `globalVariables` 声明其他静态字符串变量，并以同样的 `{{variableName}}` 语法使用。
- 身份占位符是保留名，`globalVariables` 不得覆盖。变量值只按字面插入，不进行递归模板解析。
- 所有支持模板的玩家可见文本必须通过 story-core 的集中解析器生成游戏使用的内容副本；页面组件不得自行执行零散的字符串替换，原始内容包与存档也不得保存解析后的文案。
- 玩家从设置修改身份后，已到达历史与未来文案使用新身份重新解析，不修改剧情节点 ID、已选回复或其他周目状态。
- 编辑器提供本地预览身份和解析后预览，同时保留原始占位符供作者编辑。未知、格式错误或保留名冲突的变量必须形成带字段路径的校验错误，并阻止有效内容包导出；不得把未知变量静默替换为空字符串。

### 13.2 核心翻牌节点

```json
{
  "id": "fan-a-03",
  "fanId": "fan-a",
  "title": "她发现你忘了约定",
  "postedDay": 7,
  "replyWindowDays": 7,
  "trigger": {
    "match": "all",
    "conditions": [
      { "type": "flag-set", "flag": "fan-a-promised" },
      { "type": "expired-flips-at-least", "count": 1 }
    ]
  },
  "content": {
    "text": "你是不是忘记答应过我什么了？"
  },
  "choices": [
    {
      "id": "apologize",
      "text": "对不起，我真的忘记了……",
      "cost": {
        "energy": 2,
        "mindset": 2
      },
      "effects": {
        "affinity": { "fan-a": 5 },
        "popularity": 0,
        "setFlags": ["fan-a-admitted-mistake"]
      },
      "nextNodeId": "fan-a-04a",
      "nextNodeTiming": "immediate"
    }
  ],
  "onExpire": {
    "affinity": { "fan-a": -10 },
    "setFlags": ["fan-a-ignored"]
  }
}
```

剧情文件不允许嵌入任意 JavaScript。所有条件和效果必须来自正式数据结构，以便编辑、校验和回溯。

节点触发器使用可扩展的判别联合结构。v4 首批支持：已有标记、没有标记、过期翻牌至少 N 条、已点外卖至少 N 顿；`match` 决定全部满足或任意满足。新增条件类型必须同步更新类型、校验器、引擎、编辑器和测试，不允许只在编辑器中保存引擎无法解释的字段。

## 14. 剧情图编辑器

剧情编辑器是只在开发者电脑运行的独立制作工具，与玩家游戏共享剧情数据格式和校验器，但不共享入口、路由或 UI 代码。游戏发布包只包含玩家端构建产物，不包含编辑器及节点图库依赖。

### 14.1 核心布局

- 横轴为第 1 至 30 日。
- 每名核心粉丝拥有独立故事泳道。
- 节点代表一次翻牌。
- 节点横向拖动时修改发布日期，并吸附到整数日期。
- 节点可视化展示 7 日回复期限。
- 回复选项通过端口连接到后续节点。
- 点击节点后在侧栏编辑内容、选项、消耗、效果及条件。
- 默认按单名粉丝筛选，可切换至全部故事线检查交叉关系。

### 14.2 首版功能

- 新建、复制和删除翻牌节点。
- 编辑翻牌内容与预设回复。
- 直接设置每条回复的当前粉丝好感变化和泛人气变化。
- 通过效果 JSON 设置资源以外的剧情标记、票力及跨粉丝好感效果；结构化数值输入与 JSON 始终修改同一字段。
- 连接后续节点。
- 为每条回复选择后续节点出现时机；默认日初检查，可切换为回复后立即出现。
- 编辑发布日期与期限。
- 筛选故事线。
- 导入和导出剧情文件。
- 撤销和重做。
- 自动校验剧情图。
- 分别编辑改编/原创姓名库、队伍及静态全局变量，并显示两池数量与固定抽取规则。
- 编辑核心粉丝的稳定 ID、昵称、账号、简介、标签和过往聊天；改 ID 时同步更新节点归属、好感/票力效果与延迟触发引用，避免留下半更新状态。
- 使用本地预览身份查看模板解析结果，不把预览身份写入内容包。
- 对超过 140 个字符的预设回复显示不阻塞保存的软提醒。

指定节点试玩和路线模拟属于后续增强，不是首个可用版本的发布前置条件。

### 14.3 自动校验

编辑器至少检查：

- 节点 ID 是否重复。
- 引用节点是否存在。
- 是否存在循环。
- 日期是否超出周目范围。
- 是否存在不可达节点。
- 回复是否同时消耗精力和心情。
- 非终点节点是否缺少后续走向。
- 过期结果是否有效。
- 路线决策数量是否明显超出目标游玩时长。
- 总选前是否残留无法处理的关键节点。
- 队伍 ID 与姓名库配置是否有效，队伍 ID 是否重复。
- 改编姓名是否至少 3 个，以及两个姓名池中是否存在空值、超长值或重复值。
- 静态变量名是否合法、是否覆盖身份保留名、所有模板引用是否已定义。

## 15. 待调参数

以下数值在试玩前不锁定：

- 精力和心情上限。
- 每回合基础恢复量。
- 特殊回合恢复修正范围。
- 单次外卖恢复量。
- 外卖坏结局触发次数。
- 每名粉丝初始好感度。
- 每名粉丝好感度至票力映射表。
- 泛人气至背景票力映射表。
- 年度总选名次阈值。
