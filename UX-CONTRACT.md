# UX Contract

## Product context

- Audience: Chinese-speaking 48-series fans and the game's story author.
- Primary jobs: finish a short reply-simulation run; separately author, validate, and save story graphs on a developer machine.
- Target market: Chinese-language web distribution.
- Active locales: `zh-CN`.
- Language/content register: conversational fandom-aware game copy; literal task-oriented editor copy.
- Timezone/calendar policy: the game uses fictional numbered natural days (Day 1–30), not device timezones.
- Accessibility target: WCAG 2.2 AA baseline.

## Navigation and responsive behavior

- Products and titles: the deployed game owns `成员口袋 — 工作台`; the local editor owns `剧情工坊 — Clip Simulator`.
- The game and editor are separate Vite applications and separate build outputs. Neither links to or routes into the other.
- A first visit without a valid local `PlayerProfile` opens identity setup before the member profile. The form starts with a six-choice native-radio avatar filmstrip, then a content-pack name suggestion, lets the player type or request another constrained-random name from `profileSetup.namePools`, and chooses one `profileSetup.teams` entry through an authored Select. The avatar set is app-owned and bundled: kitten, puppy, and plush-toy choices render first, followed by three original everyday fictional-idol portraits, with no stage photography, external hotlinks, or specific real-person identity. The first kitten choice is also the default. The circular choices expose accessible names but no visible caption or explanatory row; narrow screens may scroll the strip horizontally, while desktop-width viewports fit all six in one row without horizontal overflow. The team trigger shows only the selected content-defined team mark; the equal-width popup presents every team without a redundant preview rail. The first three suggestions in one form session use the adapted pool; the automatic first-visit suggestion counts as the first. When both pools contain names, later aligned five-suggestion groups shuffle exactly two adapted and three original sources; when the original pool is empty, every request falls back to adapted. The current test pack uses only 70 adapted names, one fictionalized candidate per active member in the four-team SNH48 roster snapshot. Existing-profile settings do not draw until the random button is pressed, and closing a form ends that cosmetic suggestion sequence. Source categories stay invisible to players and never enter profile or run state. Above the form, one short premise identifies the player as a new fictional 48 idol without stating an age, derives the first-election countdown from `config.totalDays`, and asks how she will answer fan flips; it does not expand resources, affinity, votes, or other rules. A returning player with a valid profile skips setup and opens the fictional member profile/workbench. Clicking “翻牌” directly resumes a playing save or creates a new run from the saved display preference. Identity editing, mode selection, and “放弃进度，从头开始” live in the member settings sheet.
- The first-visit team popup portals to the document overlay layer. The settings variant portals to the modal dialog but outside its `.settings-sheet__content` scroll owner, so Radix focus management cannot change the page or sheet scroll position when the popup opens or closes.

- Story-node trigger conditions are evaluated at initial day setup and when a later day begins by default. The day-start order is: advance the numbered day, expire overdue pending flips and apply their effects, apply the scheduled turn event and recovery, then activate every dated/unlocked node whose trigger expression passes. A choice with `nextNodeTiming: "immediate"` is the sole story-node exception: after that reply's effects are applied, the engine checks only its explicit `nextNodeId` and adds it to the pending feed when `postedDay <= currentDay` and the target trigger passes. An ineligible target stays unlocked for a later day-start check; unrelated roots and conditional nodes do not activate mid-day. Ordering takeout does not inject ordinary story nodes. The configured takeout early-ending threshold remains an independent immediate ending rule.
- The identity form uses `noValidate` and app-owned inline validation. Its avatar choices are one keyboard-operable radio group; the chosen stable app-owned ID updates the live preview immediately. The trimmed idol name is required and limited to 16 characters; team ID must match a team in the active content pack. Errors preserve all values, associate text through `aria-invalid`/`aria-describedby`, and focus the first invalid field. The random-name control is `type="button"`, never submits the form, and leaves its result editable. Radix Select owns the team popup geometry, collision behavior, and keyboard interaction.
- Game page depth is mirrored into the browser History API without changing the shareable URL. Browser Back and every in-game back control consume the same stack: settings closes before leaving the member profile, a conversation returns to the single message feed with its pre-open scroll position and row context, and the flip workbench returns to the member profile before the browser can leave the game. Committing a reply replaces its actionable conversation entry with the result entry, so Back cannot reopen an already submitted choice; returning to the feed resolves focus to that conversation's current row even when its status and position changed.
- Browser Forward restores valid game layers from the current in-memory/local save. Stale reply/result entries fall back to the nearest valid workbench or ending instead of rendering an obsolete action.
- A reply choice may reference one `earlyEndings[]` entry through `endingId`; this destination is mutually exclusive with `nextNodeId`. Before any reply or utility action enters an early ending, the game persists the exact pre-trigger playing state under an independent guarded checkpoint key. “回到上一回合” restores that state and the workbench route, clears only the temporary checkpoint, and retains the ending in `PlayerMeta`. Returning to the member menu does not silently start a new run while a recoverable ending is open; entering the flip tool returns to that ending until the player restores or explicitly abandons the run from settings.
- “翻牌” is the only actionable workbench card. The other three cards are non-interactive placeholders with explicit unavailable treatment, and no secondary quick-tool row is shown.
- The flip page header's top-right status reads “离总选结束还剩 X 天”. It derives `X` as `max(0, totalDays - currentDay)` from the active story pack and save rather than from device time, and updates after every turn transition.
- The flip workbench is one continuous message feed; pending/replied status controls ordering only and is not a selectable view. “未回复” contains only actionable core StoryNodes sorted by earliest deadline. A visible, non-interactive splitter labeled “已回复” separates them from reached history; the splitter never hides content, receives focus, or behaves like a filter. Every authored core-fan `pastChats` record is visible from Day 1 in that contact's replied history, before the numbered election-run exchanges. Its human time label such as “三个月前” replaces a fabricated Day 0 marker, and the record never enters the save or changes gameplay state. Dated ordinary-fan chatter is never a reply task: when its authored day is reached, it appears automatically in the aggregated replied history without changing the pending count, resources, affinity, popularity, flags, or votes. Core-fan conversations remain pinned before ordinary fans and each replied group sorts by recent activity. Both groups use the same conversation-row grammar, and no player-facing copy identifies ordinary fans as NPCs. Author-defined trait tags appear in the same order below the contact name on every list row; they may wrap rather than disappear. An inline empty state applies only to its own group and never replaces the other group.
- Each pending row exposes that flip's own message preview and a top-right “还有 X 天过期” label whose accessible name includes the same remaining-day value and the word “过期”. On a non-final turn, when `nextTurnDay > deadlineDay`, advancing would settle that flip as expired and the label uses the semantic danger color; when the two days are equal, the flip remains replyable next turn and the label stays muted. The final turn enters the election directly and never applies this expiry-warning state. The wording is unchanged in the danger state, so status and consequence remain understandable without color. Two pending flips from the same fan appear as two rows, with no aggregate count badge; either row can be opened and handled independently. Resolving or expiring one removes only that pending row and does not hide or reorder the other except through the normal deadline sort.
- When the latest exchange in a replied contact is expired, its list row previews that flip's concrete incoming body and the top-right status reads “已过期”; neither position uses generic “错过回复” placeholder copy. A conversation uses a light chronological chat-thread layout, repeats the list's ordered trait tags in the sticky contact title, and includes the contact's reached history plus the pending core item selected from the feed, when present. Another pending core flip from the same contact remains a separate list entry and never shares the current choice group. A centered day marker appears when the transcript enters a new content day; multiple exchanges on that day share it. Fan content is the left message, completed idol replies are right messages, and author-only context is not rendered. Every expired exchange keeps its original body and adds its own centered “这条翻牌已于第 X 日 24:00 过期” status, where `X` is that node's deadline. A read-only ordinary-fan round renders its main message plus zero to four authored continuation bubbles on the left; it never creates an idol bubble, candidate menu, result page, or gameplay effect. Every core reply cost exposes both a visible signed number plus the corresponding battery/smile icon and a complete accessible label. All player/editor-facing resource copy says “精力 / 心情”; `mindset` remains only the compatible internal field name.
- The content-pack inspector owns both relationship archives and ordinary NPC authoring. Each core fan is an independent native disclosure with editable stable ID, display name, handle, required bundled avatar ID, bio, initial affinity, vote cap, one to four ordered tags, and zero to eight past chats. Renaming a stable fan ID is an atomic editor operation that rewrites node ownership, affinity/vote-effect keys, and delayed-reply trigger references; duplicate or blank IDs remain in a local field error and never partially rewrite the pack. Past chats expose a stable record ID, human time label, fan message, and historical member reply. Each ordinary NPC round remains an independent disclosure with editable `id`, stable `contactId`, required bundled avatar ID, day, name, tag, first message, and interaction type. All rounds sharing one `contactId` update and retain one avatar ID; different ordinary contacts and core fans cannot share an ID. Automatic exchanges expose one member reply; optional read-only chatter exposes zero to four consecutive NPC bubbles. “复制为下一轮” preserves the contact identity and avatar ID, then advances the day, while delete remains recoverable through the shared editor undo history.
- Each reply card exposes a bounded “后续节点出现时机” select once a downstream node is connected. It defaults to “下一次日初检查”; “回复后立即出现” writes `nextNodeTiming: "immediate"` and explains that the target date and trigger still apply. Selecting a special ending or clearing the downstream node also clears this timing field, so the editor cannot leave an orphan timing configuration.
- Every reply card directly edits the owning fan's integer affinity delta and an integer popularity delta. Both fields are required for every choice, including zero-delta and special-ending replies. The structured numeric inputs and effects JSON edit the same values rather than maintaining duplicate state; cross-fan affinity remains available in the JSON editor. New replies start with both deltas explicitly set, and deleting popularity from JSON normalizes it back to zero.
- Preset reply text is always read before commitment and remains the same text in the candidate card, immediate sent-message result, and historical idol bubble. Long replies render in full with authored paragraph breaks and safe word wrapping. They never use line clamping, an expand/confirmation step, or an internal card scrollbar; the page/document owns scrolling, and the cost row remains after the complete text. The player never receives a free-text input.
- The reply result ticket records the owning fan's affinity change without authored commentary. Standard mode shows a directional icon and signed value; realistic mode shows the same icon with “上升 / 下降 / 不变”. Text remains visible alongside color, and a nonzero popularity delta remains a separate compact record.
- The member profile's pocket navigation is fixed to the visual viewport bottom, width-capped with the phone surface, and uses the main white account surface. The member-profile workbench grows to and behind that navigation, owning its reserved bottom/safe-area space so no main-surface gap appears between them. The labeled team chip beside “第 X 日营业中 / 准备营业” derives its surface from the selected team's `profileSetup.teams[].color` rather than a fixed global color.
- The flip workbench uses a separate fixed bottom action rail with “点外卖” and “几天后”; on the final turn the latter is labeled “进入总选”. It is fixed at visual-viewport `bottom: 0` with no outside margin or desktop-only bottom offset. The action rail uses exactly the phone frame's outer width/max-width and stays centered with it on wide viewports; it must not stretch to the desktop viewport when the phone frame is capped. Its opaque background continues through the device bottom safe-area inset so list content cannot remain visible below or through it. The flip screen reserves at least the rail's full outer height (controls plus inset), allowing the final row, empty state, scrollbar endpoint, and focused controls to scroll completely above it. The rail may show the recovery amount and whether takeout is available this turn, but never shows the accumulated takeout count. Within both rail buttons, icon and copy form one centered content cluster; the two-line takeout copy remains left-aligned inside that cluster. A successful order immediately applies the existing engine rule, then opens the canonical app-owned dialog as a compact receipt. It randomly names one of “鸡柳大人 / 椰子鸡 / 麻辣烫 / 聚湘缘 / KFC / 麦麦 / 塔斯汀”, pairs it with one of three locally bundled photographs that visibly show an external takeaway box or single-serving soup container, and repeats the fixed configured recovery from the action tip as “精力 +X / 心情 +X”. 麻辣烫 must never reuse a tabletop hotpot scene. The shop is flavor only, not a second gameplay decision; resource caps may make the state delta smaller than the advertised recovery. Escape, backdrop click, and “开吃” close it with focus restoration; if the order triggers an early ending, that ending opens only after this receipt is dismissed.
- A content-defined early-ending image renders between its heading and description inside a fixed-ratio local-media frame. It must have non-empty authored alternative text, reserve its geometry before decode, remain readable at the 390px game width, and never replace the visible ending title or description. The takeout ending uses a compressed local WebP of the fictional JBS48 post, contains no real account identity, and refers to the fictional company rather than a manager. After the current document finishes loading, the game preloads deferred local imagery in priority order—ending image, takeout imagery, fan avatars, then profile choices—through low-priority idle callbacks with at most one preload request in flight. Preloading never blocks the current render or navigation.
- Hidden statistics are a best-effort developer surface and never appear in the DOM, menus, settings, routes, achievements, or save UI. The app aggregates run starts/abandons/finishes, mode starts, replies and choice IDs, expiry counts, takeout orders, discovered endings, achievements, and election vote totals by `storyPackId@contentVersion`. Recoverable early endings increment the local ending-discovery count without closing the active run. The canonical local payload uses origin-local Local Storage and mirrors to `clip-simulator-statistics.json` in OPFS when available; `window.__CLIP_STATS__` is non-enumerable and offers only read/file/download developer access. At run start and at election or explicit abandonment, the client makes one non-blocking POST to `VITE_STATISTICS_ENDPOINT` or same-origin `/api/statistics`. The request omits credentials and referrer, uses random event/run IDs for server deduplication, sends only a minimal run/result summary, is never retried, and produces no player feedback. It sends no player profile, message copy, per-node choice history, or stable device ID. Network, Local Storage, or OPFS failure is silent and cannot change game state. Cross-device aggregation exists only if the deployment implements the endpoint.
- Game is phone-first and centered on wide screens. Editor is desktop-first; below 900px the inspector follows the canvas in document flow.
- Focused controls must not sit behind the mobile action bar; safe-area and scroll margins are mandatory.
- Unknown hash routes return to a small app-owned not-found surface with links to game/editor.

## Identity and template resolution

- `PlayerProfile` contains `idolName`, the stable `teamId`, and an app-owned `avatarId`. It is stored under an independent guarded local-storage key with in-memory fallback, not inside `GameState`, achievements, or the content pack. Restarting or replacing a run never clears it; clearing site data does. Older or unknown avatar IDs normalize to the first bundled avatar without invalidating the profile; if its team no longer exists in the active pack or its name fails validation, the game returns to identity setup instead of guessing a team.
- Saving a valid identity from settings applies immediately without restarting or changing resources, affinity, story flags, or vote logic. Because content is resolved at render/load time rather than snapshotted into the save, changing identity re-renders both historical and future player-visible text with the new profile.
- The reserved runtime variables are `{{idolName}}`, `{{idolNickname}}`, `{{teamName}}`, and `{{teamShortName}}`; `idolNickname` repeats the final character of the trimmed idol name, while `teamName` and `teamShortName` come from the profile's selected team. The content pack may add literal strings through top-level `globalVariables`, but cannot override a reserved name.
- One story-core resolver builds the variable context and transforms every supported player-visible content field for both the game and editor preview. Raw JSON and saved choice IDs remain unresolved. Resolution is a single pass: values inserted from a profile or `globalVariables` are treated as literal text and are not parsed again as templates.
- The editor provides a local preview identity, renders resolved text beside authoring context, and keeps raw placeholders in the saved pack. Unknown or malformed variables stay visible in preview and produce a persistent validation error that blocks validated export/apply; the runtime never silently replaces them with an empty string.

## Overlays and feedback

- Dialog primitive: app-owned wrapper around native HTML `dialog`, with explicit title/actions, Escape handling, and focus restoration.
- Destructive confirmation: deleting a node is recoverable through editor history but still receives a warning confirmation because edges may change.
- Toasts: one bottom-center live region, deduplicated; routine messages dismiss automatically and are never the only error source.
- Unsaved changes: editor changes stay in memory until explicitly saved/downloaded. A dirty indicator and browser leave warning protect the draft; the game never reads editor memory.
- Layer order: graph < sticky toolbars < inspector < dialog < toast.

## Async and resilience

- No remote mutations exist.
- Game saves use guarded `localStorage` access with in-memory fallback for the current session. Recoverable early endings use a separate compatible playing-state checkpoint that is removed after restoration or explicit run reset.
- The independent `PlayerProfile` uses the same guarded-storage behavior but a separate key and lifecycle from the run save. A storage write failure keeps the accepted profile for the current in-memory session and never erases the active run.
- Editor drafts use guarded local storage, while explicit save writes or downloads a validated JSON content file. Import/open failures never replace the active draft.
- Multi-tab edits use last-local-write-wins; the first version does not claim collaborative consistency.
- File import is parsed and validated before commit. No automatic retries or background jobs exist.

## Validation

- Zod owns structural content validation; graph validation owns references, cycles, dates, reachability, and pacing warnings.
- Story-pack validation owns unique teams, ordinary-flip IDs, one required known avatar ID for each core fan and ordinary contact, cross-character avatar uniqueness, same-contact multi-round avatar consistency, the mutually exclusive ordinary display modes (`reply` versus `continuations`), ordinary-flip day bounds, the adapted-pool minimum and cross-pool uniqueness of configured profile names, one to four concise and unique tags per core fan, zero to eight structurally complete past chats with per-fan unique IDs, valid static variable names, reserved-name collisions, and unknown/malformed template references. The original pool may be empty. Template errors include the source path and node ID when applicable.
- Editor fields update the local draft immediately; validation updates after each committed change.
- Reply text longer than 140 characters produces an editor warning, not a schema error; it never blocks save/export. The editor and player preserve authored paragraph breaks.
- Import and apply-preview actions show a persistent validation summary and do not rely on toasts.
- Forms use `noValidate`; textareas use `resize: none`; invalid controls expose visible text and ARIA state.
